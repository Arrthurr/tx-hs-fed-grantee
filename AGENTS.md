# Texas Head Start Interactive Map — Agent Guide

## Project Snapshot

React 18 + TypeScript + Vite 7 application for visualizing Texas Head Start
and Early Head Start federal grantee programs on Google Maps. Features include
program search, layer controls, a separate details panel, and four TXHSA regions
(West, North, East, South) generated by dissolving county polygons.

Stack: `@vis.gl/react-google-maps`, Tailwind CSS, Lucide React, Jest with React
Testing Library, and Playwright infrastructure. Region generation uses
`@turf/union` and `tsx`.

## Commands

Run from the repository root. CI uses Node.js 22.

```bash
npm run dev            # Start Vite dev server
npm run build          # Production build; outputs to dist/
npm run build:regions  # Regenerate committed TXHSA region GeoJSON
npm run preview        # Preview production build
npm run lint           # ESLint
npm run typecheck      # TypeScript app + node configs
npm test               # Jest unit tests
npm run test:advisories  # High/critical npm advisory gate
npm run test:e2e       # Playwright loading recovery and map accessibility
npm run test:e2e:ui    # Playwright UI mode
```

`npm run build` does not replace `npm run typecheck`; run both when verifying
application changes.

## Environment and Security

Create `.env.local` in the repository root:

```env
VITE_GOOGLE_MAPS_API_KEY=your_google_maps_api_key_here
# Optional custom Google Maps Map ID:
VITE_GOOGLE_MAPS_MAP_ID=your_map_id_here
```

- A valid Google Maps API key is required for runtime map rendering.
- Never commit `.env.local`, credentials, or secret values.
- Vite exposes `VITE_`-prefixed variables to browser code. These values are
  public, not a place for server-side secrets.
- The Google Maps browser key is necessarily client-visible. Restrict it by
  authorized website referrers and required APIs in Google Cloud.
- Restart the dev server after changing environment variables. Set production
  Vite variables before building.
- Files under `public/` are publicly served; keep sensitive data out of static
  assets, including JSON and GeoJSON.
- Serve production over HTTPS and keep dependencies updated for security fixes.
- Advisory ownership, cadence, and remaining exceptions live in `docs/security/advisory-review.md`. Do not run `npm audit fix --force`.

## Architecture and Navigation

- `src/components/TexasMap.tsx`: Google Maps, program markers, one
  `google.maps.Data` overlay per region, and program/region details outside the map.
- `src/components/MapControls.tsx`: collapsible layer visibility controls; no dragging.
- `src/components/SearchBar.tsx` and `SearchResults.tsx`: program search UI.
- `src/components/LoadingSpinner.tsx` and `ErrorDisplay.tsx`: loading/error UI.
- `src/hooks/useMapData.tsx`: shared provider, loaders, errors, retries, layer
  visibility, and memoized counts. Production consumers use `useMapData()`
  inside a single `MapDataProvider`; avoid separate internal loaders per consumer.
- `src/hooks/useSearch.ts`: case-insensitive substring search over program
  names, addresses, and grantees; returns programs only.
- `src/data/headStartPrograms.ts`: program validation and processing.
- `src/data/txhsaRegions.ts`: region validation, processing, and authored
  `REGION_FUNDED_AMOUNTS`.
- `src/data/tdemCountyRegions.ts`: county-to-TDEM lookup, merge mapping, overrides.
- `src/utils/geometry.ts`: point-in-polygon helpers. GeoJSON coordinates are
  `[longitude, latitude]`; helper arguments are `(lat, lng)`.
- `src/utils/mapHelpers.ts` and `src/types/maps.ts`: helpers and shared types.
- `src/App.tsx` and `src/main.tsx`: application composition and entry point.
- `scripts/build-txhsa-regions.ts`: repeatable region-generation script.

## Data Sources

Program data:
- Runtime file: `public/assets/geojson/headStartPrograms.json`
- Helpers/tests: `src/data/headStartPrograms.ts` and its adjacent test file.

TXHSA region data:
- Build-only county source: `scripts/source/tx-counties.geojson`
- County lookup and overrides: `src/data/tdemCountyRegions.ts`
- Build script: `scripts/build-txhsa-regions.ts`
- Committed runtime outputs: `public/assets/txhsa-geojson/{west,north,east,south}.geojson`

Each generated file is a single-feature `FeatureCollection` with
`properties.name` set to its region name. Preserve both `Polygon` and
`MultiPolygon` support.

Keep the county source outside `public/`: it is build-only input. Do not
manually edit generated region files except to repair a generated-file problem.
Update the inputs, run `npm run build:regions`, and commit regenerated outputs.

## TXHSA Region Rules

### Membership and validation

The build has three layers:

1. `tdemCountyRegions` is the factual county-to-TDEM lookup. Do not rewrite
   TDEM numbers to force a TXHSA presentation change.
2. `tdemToTxhsaRegion` merges eight TDEM regions: 1 and 7 → West; 2 and 3 →
   North; 4 and 8 → East; 5 and 6 → South.
3. `txhsaCountyOverrides` assigns specific counties directly to a TXHSA region,
   taking precedence over the merge mapping without changing their TDEM number.

Use overrides sparingly for deliberate, reviewable county-level exceptions.
Current overrides assign Houston, Shelby, Nacogdoches, Polk, San Jacinto,
Smith, Trinity, Jefferson, and Orange to East.

County names must match the source's `COUNTY` property with trailing
`" County"` removed and whitespace trimmed. Use `San Jacinto` and `La Salle`,
not `LaSalle`.

Preserve intentional build failures for invalid source collections, missing
county names, source counties missing from the TDEM lookup (even with an
override), unknown override keys, empty regions, and failed dissolves.
Sparse test fixtures may explicitly disable the populated-region requirement;
normal builds retain it.

Disconnected county assignments can legitimately produce `MultiPolygon`
geometry. Review whether the disconnect is intended rather than forcing a
single polygon. Regions should cover Texas without gaps or overlapping areas.
Review source changes and verification results rather than relying on large
minified coordinate diffs alone.

### Runtime behavior and counts

- Program markers default on; region overlays default off.
- Both datasets load on mount, including the four region files in parallel;
  enabling the overlay does not initiate its first load.
- Validate region features before processing. Preserve all-or-nothing region
  loading rather than rendering a partial overlay.
- `regionProgramCounts` is memoized and remains `null` while either dataset is
  empty. Counts are independent of layer visibility and search.
- Assign each program by coordinates. Counts are published only when every
  accepted program matches exactly one region. Zero or multiple matches
  (including shared outer edges) withhold all counts. Do not resolve
  overlaps by West/North/East/South array order.
- Overrides affect counts through generated county geometry, not program county
  labels; they are not program-level exceptions.
- Region info windows show name, program count, and total funded amount.
  Amounts come from product-owner-authored `REGION_FUNDED_AMOUNTS`, not an
  aggregation of program funding. Preserve that source unless requirements change.

## Code Conventions

- Components use PascalCase filenames/names under `src/components/`.
- Hooks use camelCase `use*` names; utilities and type files use camelCase.
- Tests generally sit beside source as `.test.ts` or `.test.tsx`; script tests
  live under `scripts/__tests__/`.
- Follow existing typed arrow-function components, `ComponentNameProps`
  interfaces, `React.FC<Props>`, and destructured props where appropriate.
  Mark genuinely optional props with `?`.
- Group imports as React, third-party libraries, then local components, hooks,
  types, and utilities, following the surrounding file.
- Keep strict typing, explicit `null` for nullable state, and meaningful defaults.
- Prefer `useCallback` for child handlers when it matches local patterns.
- Prefer existing React/Tailwind patterns over new abstractions.
- Report errors through React state and user-friendly UI. Preserve the program
  loader's error classification, bounded exponential retries, and request/timer
  cleanup. Avoid duplicate retry loops and fallbacks that hide invalid inputs.

### Styling and accessibility

- Prefer Tailwind utilities and existing classes (`btn-`, `card-`, `marker-`),
  with template literals or `clsx` for conditional classes.
- Global styles: `src/styles/design-system.css`; theme: `tailwind.config.js`.
- Reuse `--txhsa-west`, `--txhsa-north`, `--txhsa-east`, `--txhsa-south`, and
  `--txhsa-accent` tokens and existing responsive breakpoint patterns.
- Preserve semantic controls, accessible names, ARIA state, keyboard interaction,
  and screen-reader announcements for dynamic content.
- Target WCAG AA contrast; do not assume existing UI has been audited.

## Testing and Verification

Jest covers components, hooks, processing, geometry, helpers, and region builds.
Use React Testing Library for interactions and mock Google Maps/network calls.

```bash
npm test
npm test -- src/components/TexasMap.test.tsx
npm test -- --coverage
```

Jest is configured with `watchman: false`. For application changes, run
relevant tests, lint, typecheck, and production build. CI runs these checks,
including the full Jest suite and `npm run test:advisories`.

For TXHSA region changes, run at least:

```bash
npm run build:regions
npm test -- scripts/__tests__/build-txhsa-regions.test.ts src/hooks/useMapData.test.ts
npm run typecheck
npm run lint
npm run build
```

For browser-relevant changes, verify map loading, program markers, search,
program details, and the TXHSA Regions toggle, overlays, region buttons and details.
Check focus return, fullscreen selection and resizing. Use a valid Google Maps API
key for live-map checks.

Playwright covers loading recovery, map accessibility, and directory chrome
with an SDK test double. CI runs that suite on Chromium. Live Google Maps
smoke is opt-in via `LIVE_GOOGLE_MAPS=1` and is not a CI secret consumer.
Read `src/e2e/README.md` before adding tests. Use current UI selectors, not
removed controls or nonexistent mock hooks. Playwright can start Vite.

Existing `useMapData.test.ts` React `act(...)` warnings may occur. Distinguish
them from new regressions; passing tests do not imply warnings were resolved.
